السلام عليكم ورحمة الله وبركاته 👋

في المنشور ده حابب أتكلم عن **تأمين البرمجيات (Software Security)**، وأشهر الطرق والثغرات اللي ممكن يستغلها المهاجمون للوصول إلى بيانات المستخدمين أو تنفيذ أوامر غير مصرح بها.

هنبدأ بأسلوب احتيال مشهور اسمه **Phishing**، وبعدها هنتكلم عن واحدة من أشهر ثغرات تطبيقات الويب، وهي **Cross-Site Scripting (XSS)**، وهنشرح أنواعها وطرق الحماية منها.

> **ملاحظة:** الأمثلة الموجودة في المقال تعليمية، وهدفها فهم آلية عمل الثغرات وكيفية الوقاية منها.

---

## أولًا: الـ Phishing 🎣

### يعني إيه Phishing؟

الـ **Phishing** هو أسلوب احتيال بيحاول فيه المهاجم خداع المستخدم وإقناعه إن رابطًا أو صفحةً معينة تابعة لجهة موثوقة، بينما هي في الحقيقة قد تكون صفحة مزيفة أنشأها المهاجم.

الهدف غالبًا هو سرقة بيانات تسجيل الدخول، أو معلومات حساسة، أو إقناع الضحية بتنفيذ إجراء معين.

والـ Phishing مش ثغرة برمجية بالضرورة، لكنه بيعتمد على **الهندسة الاجتماعية (Social Engineering)**، أي استغلال ثقة المستخدم أو عدم انتباهه.

### إزاي بيحصل الهجوم؟

من الطرق الشائعة استخدام روابط يظهر فيها نص موثوق، لكن الرابط الفعلي يشير إلى نطاق مختلف.

### مثال:

```html
<a href="https://goog1e.com">Google</a>
```

النص اللي هيظهر للمستخدم هو:

**Google**

لكن عند الضغط عليه، المتصفح هيروح إلى:

```text
https://goog1e.com
```

وده نطاق مختلف عن `google.com`.

> المثال افتراضي للتوضيح، ومجرد اختلاف النطاق لا يعني بالضرورة أن الموقع خبيث.

المهاجم ممكن ينشئ صفحة تشبه صفحة تسجيل الدخول الأصلية، ويطلب من المستخدم إدخال البريد الإلكتروني وكلمة المرور. لو المستخدم أدخل بياناته، ممكن يتم إرسالها إلى خادم يتحكم فيه المهاجم.

وممكن كمان الرابط يوجه المستخدم إلى صفحة تبدو فارغة، لكنها تحتوي على محتوى أو سكربتات تحاول استغلال ثغرات أخرى في المتصفح أو الموقع. لكن مجرد فتح صفحة لا يعني تلقائيًا أن المهاجم يستطيع سرقة كل بيانات المتصفح.

### هل يقدر الموقع الخبيث يسرق الـ Cookies؟

هنا لازم نفرق بين حاجتين:

#### 1. Same-Origin Policy (SOP)

الـ **Same-Origin Policy** هي آلية أمان في المتصفحات بتقيّد قدرة JavaScript الموجود في Origin معين على قراءة البيانات الخاصة بـ Origin مختلف.

والـ Origin بيتحدد من خلال:

- البروتوكول مثل `https`.
- اسم النطاق (Host).
- رقم المنفذ (Port).

مثلًا:

```text
https://example.com
https://attacker.com
```

الموقعان لهما Origin مختلف، وبالتالي JavaScript الموجود في `attacker.com` لا يستطيع ببساطة قراءة محتوى صفحات `example.com` أو بياناتها المحمية بواسطة سياسات المتصفح.

لكن الـ SOP مش جدار حماية شامل ضد كل الهجمات. بعض الطلبات بين المواقع ممكن تكون مسموحة، والكوكيز قد تُرسل تلقائيًا مع بعض الطلبات حسب إعدادات `SameSite` وغيرها من السياسات.

#### 2. خصائص حماية الـ Cookies

الكوكيز الحساسة يُفضل ضبط خصائصها بشكل صحيح، مثل:

- `HttpOnly`: تمنع JavaScript من قراءة الكوكي مباشرة باستخدام `document.cookie`.
- `Secure`: تجعل إرسال الكوكي مقتصرًا على الاتصالات الآمنة عبر HTTPS، مع مراعاة استثناءات بيئة localhost.
- `SameSite`: تتحكم في إرسال الكوكيز مع الطلبات العابرة للمواقع، وتساعد في تقليل بعض هجمات CSRF.

هنرجع للنقطة دي بالتفصيل لما نتكلم عن حماية تطبيقات الويب.

### إزاي نحمي نفسنا من الـ Phishing؟

1. **راجع الرابط قبل الضغط عليه.** اعمل Hover على الرابط وشوف العنوان الفعلي اللي بيظهر في أسفل المتصفح.
2. **راجع اسم النطاق بعناية.** وجود اختلاف بسيط في الحروف ممكن يكون علامة على رابط مزيف.
3. **متدخلش بياناتك في صفحة وصلت لك من مصدر غير موثوق.**
4. لو الرسالة بتطلب منك تسجيل الدخول، افتح الموقع الرسمي بنفسك بدل ما تضغط على الرابط.
5. استخدم مدير كلمات مرور موثوق؛ غالبًا يقدر يميز بين النطاق الأصلي والنطاق المزيف.
6. فعّل المصادقة متعددة العوامل (MFA) لتقليل أثر تسريب كلمة المرور.

مثال على الفرق بين نطاقين:

```text
google.com   -> النطاق الأصلي
goog1e.com   -> نطاق مختلف
```

## ثانيًا: Cross-Site Scripting (XSS) 💻

### يعني إيه XSS؟

الـ **Cross-Site Scripting (XSS)** هي ثغرة أمنية بتحصل لما تطبيق ويب يتعامل مع بيانات غير موثوقة بطريقة تسمح للمتصفح بتفسيرها على إنها كود JavaScript بدل ما يتعامل معاها كنص عادي.

بمعنى أبسط: الموقع بياخد Input من المستخدم، وبعد كده يعرضه داخل الصفحة من غير ما يضمن إنه آمن، فيقدر المهاجم يحقن كود يتم تنفيذه في متصفح الضحية.

### ليه الاختصار XSS بدل CSS؟

الاختصار جاي من:

```text
Cross-Site Scripting
```

وحرف **X** هنا مأخوذ من كلمة *Cross*، وليس بسبب وجود تعارض مع CSS.

### مثال بسيط

تخيل إن عندنا موقع فيه خانة بحث، والمستخدم الطبيعي بيكتب:

```text
herbs for headache
```

لكن مهاجم ممكن يحاول إدخال:

```html
<script>alert("attack")</script>
```

الكود ده بيحاول تشغيل JavaScript يعرض نافذة منبثقة فيها كلمة `attack`.

لو الموقع أخذ المدخلات وحطها داخل صفحة HTML بطريقة غير آمنة، ممكن المتصفح يفسرها ككود بدل ما يعرضها كنص.

**المشكلة مش في وجود JavaScript داخل Input بحد ذاته،** لكن في إن التطبيق سمح للمدخلات غير الموثوقة إنها تتحول إلى كود قابل للتنفيذ في سياق الصفحة.

### ليه XSS خطيرة؟

حسب مكان تنفيذ الكود وصلاحيات الصفحة، ممكن المهاجم يستخدم XSS في:

- تغيير محتوى الصفحة المعروض للمستخدم.
- إنشاء نماذج مزيفة لطلب بيانات حساسة.
- تنفيذ إجراءات باسم المستخدم، إذا كانت الحماية والصلاحيات تسمح بذلك.
- قراءة بيانات موجودة في الصفحة ويمكن للـ JavaScript الوصول إليها.
- استغلال صلاحيات المستخدم داخل التطبيق.

ولو كان المستخدم Admin، فقد تكون العواقب أكبر بكثير.

---

## ثالثًا: أنواع الـ XSS

فيه ثلاثة أنواع رئيسية بنقابلها عند دراسة XSS:

1. Reflected XSS
2. Stored XSS
3. DOM-based XSS

---

## النوع الأول: Reflected XSS

### الفكرة

في الـ **Reflected XSS**، المهاجم بيضع Payload داخل Request، مثل قيمة في URL أو خانة بحث.

السيرفر بياخد القيمة دي، ويرجعها في الـ HTTP Response داخل صفحة HTML بطريقة غير آمنة.

لو المتصفح فسّر القيمة على إنها كود، ممكن يتم تنفيذ JavaScript.

### مثال توضيحي

تخيل موقع عنده صفحة بحث:

```text
https://example.com/search?q=herbs
```

السيرفر ممكن يعرض:

```html
<h1>Search results for: herbs</h1>
```

لكن لو السيرفر بيُدخل قيمة `q` داخل HTML بدون معالجة مناسبة، فقد يكون هناك خطر XSS.

مثلًا، Payload تعليمي:

```html
<script>alert('attack')</script>
```

لو اتعكس داخل سياق HTML قابل للتنفيذ، ممكن المتصفح ينفذه.

### إزاي الـ Payload بيظهر في الـ URL؟

عشان نبعت أحرف خاصة داخل URL، ممكن نستخدم **URL Encoding**.

مثلًا:

```text
https://example.com/search?q=%3Cscript%3Ealert%28%27attack%27%29%3C%2Fscript%3E
```

الجزء ده:

```text
%3Cscript%3Ealert%28%27attack%27%29%3C%2Fscript%3E
```

هو تمثيل مُرمّز للنص التالي:

```html
<script>alert('attack')</script>
```

لكن مهم نفهم إن URL Encoding مش وسيلة حماية من XSS. هو مجرد طريقة لتمثيل البيانات داخل URL.

لو التطبيق فك الترميز وأدخل القيمة في سياق HTML بطريقة غير آمنة، ممكن تحصل الثغرة.

### ليه اسمها Reflected؟

لأن القيمة اللي المهاجم بعتها في الـ Request بتنعكس مرة أخرى في الـ Response، ثم قد يتم تفسيرها ككود داخل الصفحة.

### هل كل قيمة في URL ممكن تسبب XSS؟

لا.

وجود Payload في الرابط وحده مش معناه إن الموقع عنده ثغرة. لازم التطبيق يعرض القيمة في سياق يسمح بتنفيذها، ويكون فيه فشل في تطبيق الحماية المناسبة.

## النوع الثاني: Stored XSS

### الفكرة

في الـ **Stored XSS**، المهاجم بيحاول إدخال محتوى خبيث يتم تخزينه داخل التطبيق، مثل:

- قاعدة البيانات.
- نظام إدارة المحتوى.
- التعليقات.
- المقالات.
- رسائل المستخدمين.
- ملفات أو بيانات يتم الاحتفاظ بها ثم عرضها لاحقًا.

بعد كده، لما مستخدم آخر يفتح الصفحة اللي فيها المحتوى، ممكن المتصفح ينفذ الكود إذا كان التطبيق بيعرضه بطريقة غير آمنة.

### مثال

تخيل عندنا موقع بيسمح للمستخدمين بكتابة تعليقات:

```text
Karim: This herb is useful.
```

لكن مهاجم أضاف تعليقًا يحتوي على محتوى HTML أو JavaScript غير موثوق.

لو الموقع خزّن التعليق وعرضه لاحقًا باستخدام طريقة غير آمنة، ممكن الكود يتنفذ عند كل مستخدم يفتح صفحة التعليقات.

### ليه Stored XSS ممكن تكون أخطر؟

لأن المهاجم مش لازم يبعت رابطًا جديدًا لكل ضحية.

يكفي إن المحتوى الخبيث يتخزن في مكان بيزوره مستخدمون آخرون، مثل صفحة المقالات أو التعليقات.

لكن مستوى الخطورة بيعتمد على:

- عدد المستخدمين اللي ممكن يشوفوا المحتوى.
- صلاحيات المستخدمين.
- مكان عرض المحتوى.
- نوع البيانات اللي يقدر JavaScript يوصل إليها.
- وجود وسائل حماية إضافية.

### مثال على سيناريو خطير

لو فيه لوحة تحكم خاصة بالـ Admin بتعرض تعليقات المستخدمين، والموقع عنده Stored XSS، فقد يتم تنفيذ الكود داخل سياق لوحة التحكم عندما يفتح الـ Admin التعليق المصاب.

وده ممكن يؤدي إلى إجراءات غير مصرح بها إذا كانت هناك ثغرات أخرى أو حماية غير كافية.

## النوع الثالث: DOM-based XSS

### الفكرة

الـ **DOM-based XSS** بتحصل غالبًا لما JavaScript الموجود في المتصفح يقرأ بيانات غير موثوقة من مصدر مثل:

- `location.search`
- `location.hash`
- `document.referrer`

وبعد كده يحط البيانات دي داخل الصفحة باستخدام طريقة غير آمنة.

في النوع ده، تنفيذ الكود ممكن يحصل بالكامل داخل المتصفح من غير ما السيرفر يعكس الـ Payload في الـ Response.

### مثال غير آمن

```html
<div id="output"></div>

<script>
  const value = location.hash.substring(1);

  document.getElementById("output").innerHTML = value;
</script>
```

لو المستخدم فتح رابطًا يحتوي على قيمة يتم تفسيرها كـ HTML، فإن استخدام `innerHTML` هنا قد يسمح بحقن محتوى غير موثوق.

### الطريقة الأكثر أمانًا في المثال

لو إحنا عاوزين نعرض القيمة كنص فقط، نستخدم `textContent`:

```html
<div id="output"></div>

<script>
  const value = location.hash.substring(1);

  document.getElementById("output").textContent = value;
</script>
```

الفرق إن `textContent` بيعرض المحتوى كنص، بدل ما يفسره كـ HTML.

> ملاحظة: `textContent` مناسب لعرض النصوص، لكنه لا يكفي وحده لكل السياقات. لو التطبيق محتاج يسمح ببعض HTML، لازم يستخدم Sanitization مناسبًا ومختبرًا.

## رابعًا: إزاي نحمي تطبيقات الويب من XSS؟ 🛡️

الحماية من XSS مش بتعتمد على إجراء واحد. الأفضل استخدام مجموعة من طبقات الحماية.

### 1. Output Encoding

لما نعرض بيانات المستخدم داخل HTML، لازم نعمل Encoding مناسب للسياق اللي هتظهر فيه البيانات.

مثلًا، لو المستخدم كتب:

```html
<script>alert("attack")</script>
```

وإحنا عاوزين نعرضها كنص، لازم المتصفح يشوفها كنص عادي، مش كـ HTML قابل للتنفيذ.

في HTML، الأحرف الخاصة ممكن يتم تمثيلها بكيانات (Entities)، مثل:

```html
&lt;script&gt;alert("attack")&lt;/script&gt;
```

لكن مهم نعرف إن الـ Encoding بيعتمد على السياق. التعامل مع النص داخل HTML يختلف عن التعامل معه داخل JavaScript أو CSS أو URL.

### 2. Input Validation

الـ **Input Validation** معناها إننا نتحقق من البيانات اللي المستخدم بيدخلها.

مثلًا:

- هل البريد الإلكتروني مكتوب بصيغة صحيحة؟
- هل العمر رقم؟
- هل الحقل مطلوب؟
- هل القيمة ضمن الحدود المسموحة؟

لكن لازم ننتبه إن Validation وحدها مش كافية لمنع XSS.

لأن المهاجم ممكن يدخل بيانات تبدو صحيحة من ناحية الشكل، لكنها تصبح خطيرة عند عرضها في سياق غير آمن.

عشان كده لازم نستخدم Output Encoding أو Sanitization حسب الحالة.

### 3. تجنب استخدام innerHTML مع بيانات غير موثوقة

الكود ده ممكن يكون خطرًا لو `username` جاي من المستخدم:

```javascript
element.innerHTML = username;
```

لو الهدف مجرد عرض نص، الأفضل:

```javascript
element.textContent = username;
```

وكمان لازم ننتبه إلى بعض الطرق الأخرى التي قد تفسر HTML أو تتسبب في تنفيذ JavaScript، مثل:

- `insertAdjacentHTML`
- `document.write`
- بعض استخدامات `outerHTML`
- بعض خصائص DOM التي تتعامل مع HTML

مش معنى كده إن كل استخدام لهذه الخصائص ثغرة، لكن لازم نعرف مصدر البيانات ونستخدم API مناسبة.

### 4. Content Security Policy (CSP)

الـ **Content Security Policy** هي HTTP Security Header بتسمح للموقع بتحديد مصادر المحتوى المسموح للمتصفح بتحميله أو تنفيذه.

مثلًا:

```http
Content-Security-Policy: script-src 'self' https://cdn.example.com
```

المعنى هنا إن تحميل السكربتات مسموح من نفس الموقع ومن المصدر المحدد.

لكن CSP مش بديل عن إصلاح الثغرة نفسها. هي طبقة دفاع إضافية بتقلل احتمالية استغلال بعض أنواع XSS.

وفي التطبيقات الحديثة، استخدام سياسات تعتمد على `nonce` أو `hash` قد يكون أنسب من السماح بمصادر عامة، حسب تصميم التطبيق.

### 5. استخدام HttpOnly للكوكيز الحساسة

لو عندنا Cookie خاصة بجلسة المستخدم، من الأفضل غالبًا تفعيل `HttpOnly`:

```http
Set-Cookie: sessionId=example; HttpOnly; Secure; SameSite=Lax
```

خاصية `HttpOnly` تمنع JavaScript من قراءة الكوكي باستخدام:

```javascript
document.cookie
```

لكن لازم نفهم إنها لا تمنع تنفيذ XSS نفسه.

حتى لو المهاجم مش قادر يقرأ Session Cookie، ممكن يستغل XSS في تنفيذ إجراءات داخل التطبيق باسم المستخدم، إذا كانت صلاحيات الجلسة تسمح بذلك.

### 6. استخدام Frameworks بشكل صحيح

أغلب الـ Frameworks الحديثة، مثل React، بتعمل Escaping افتراضي للقيم النصية عند عرضها.

مثلًا:

```jsx
function UserName({ name }) {
  return <h1>{name}</h1>;
}
```

لو `name` جاي من المستخدم، React عادةً يعرضه كنص بدل ما يفسره كـ HTML.

لكن لازم ناخد بالنا من استخدام APIs أو خصائص تسمح بإدخال HTML خام، مثل:

```jsx
<div dangerouslySetInnerHTML={{ __html: content }} />
```

لو `content` غير موثوق ومش معمول له Sanitization مناسب، فقد يؤدي ذلك إلى XSS.

### 7. تحديث المكتبات ومراجعة الكود

من المهم:

- تحديث المكتبات والإضافات باستمرار.
- مراجعة أي مكان بيعرض محتوى المستخدم.
- استخدام أدوات فحص الثغرات.
- اختبار الـ Input والـ Output في كل جزء من التطبيق.
- عدم الاعتماد على الحماية الافتراضية للـ Framework وحدها.

| Reflected XSS | داخل Request، مثل URL | غالبًا عن طريق رابط أو طلب خاص |
| Stored XSS | محتوى مخزن في التطبيق | عند عرض الصفحة التي تحتوي على المحتوى |
| DOM-based XSS | بيانات يعالجها JavaScript داخل المتصفح | عند تشغيل الكود الذي يتعامل مع البيانات بشكل غير آمن |

---

## سادسًا: هل HttpOnly بتحل مشكلة XSS؟

الإجابة: **لا، مش بشكل كامل.**

خلينا نفترض إن عندنا Cookie خاصة بجلسة المستخدم:

```http
Set-Cookie: sessionId=abc123; HttpOnly; Secure; SameSite=Lax
```

لو حصل XSS، فإن:

```javascript
document.cookie
```

لن يعرض الكوكي التي تحمل `HttpOnly`.

لكن JavaScript الخبيث قد يظل قادرًا على:

- قراءة بيانات موجودة داخل الصفحة.
- تعديل عناصر الواجهة.
- إرسال طلبات إلى الـ Backend من داخل سياق الموقع.
- تنفيذ إجراءات يملك المستخدم صلاحية تنفيذها.

عشان كده حماية الكوكيز مهمة، لكنها مش بديل عن إصلاح XSS.

## الخلاصة 🎯

في المقال ده اتكلمنا عن الفرق بين **Phishing**، اللي هو أسلوب احتيال بيعتمد على خداع المستخدم، وبين **XSS**، اللي هي ثغرة بتسمح بتنفيذ JavaScript غير موثوق داخل سياق صفحة ويب.

واتعرفنا على ثلاثة أنواع رئيسية من XSS:

- Reflected XSS
- Stored XSS
- DOM-based XSS

وكمان اتكلمنا عن طرق الحماية، زي:

- Output Encoding.
- Input Validation.
- استخدام `textContent` بدل `innerHTML` عند عرض النصوص.
- Content Security Policy.
- HttpOnly وSecure وSameSite.
- استخدام Frameworks بشكل صحيح.

**أهم حاجة:** تأمين تطبيقات الويب مش مجرد إضافة Header أو تفعيل خاصية واحدة. هو مجموعة من الممارسات اللي لازم تتطبق من وقت تصميم التطبيق لحد كتابة الكود واختباره وصيانته.

والتعلم الحقيقي للأمن السيبراني بيبدأ من فهم إزاي الثغرات بتحصل، وبعد كده إزاي نمنعها ونكتب كود أكثر أمانًا. 🔐
